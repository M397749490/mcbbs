风筝类物品可以从 地图上随机生成的 散落的风筝 和 被遗忘的儿时宝藏 获得。
共有三件物品

破风筝
id:"journey:broken_kite"

  也许是谁家小孩子放风筝时断线了，
  于是这风筝便被吹飞到了天涯海角，荒山野岭。
  似乎不是最近的事情。
  这个风筝那么大，一定很好玩，真是可惜呀。

       破风筝实质上是一个有限耐久、无法修复、用完就消失的鞘翅，取下来时会变成皮衣，耐久保存在专门的NBT里（KiteDamage，数据类型为short），因而无法修复。

       可从散落的风筝、儿时宝藏获取

木柄线轴
id:"journey:wooden_spool"

  失去风筝后，也就失去了用途，只能无奈雪藏。
  不过，就算只剩线轴其实也挺好玩的。

木柄线轴的作用有两个：
              一个是使用后存储的坐标作为使用旧风筝线传送时的目标，一个则是设置默认的出生点而不影响正常通过床设置重生点。
              设置默认的重生点的意思是说，如果玩家死亡后没有床或者已损坏，就会重生在设定的点，就像一个“个人的setworldspawn”

       可从遗忘的儿时宝藏获取

旧风筝线
id:"journey:the_old_kite_string"


  一段泛黄的风筝线，依旧是十分的强劲

        旧风筝线，可以让玩家瞬间回到标记的点。

        通过散落的风筝和儿时宝藏都可以获取。

没什么技术的技术总结。

一·所谓“设置个人默认重生点”
1.用一个我称作event的模块检测玩家的复活事件
   原理是利用@e不能选择到已死亡的实体，加上deathCount.
2.如果玩家没有床等重生点，或者重生点被破坏，则玩家的，用于储存重生点信息的数据标签SpawnX、SpawnY、SpawnZ会在复活之后消失，并且无法被检测到。
3.当检测到玩家：1.拥有重生的tag（模块接口）；2.拥有使用过 木柄线轴 的tag；3.没有SpawnX数据标签 时，执行传送模块，将玩家传送到记分板记录的点。

二·网格点式结构生成





由于机制略复杂，这里我先下几个定义。
   网格点：x坐标和z坐标均为3200的倍数的点即为一个网格点，其坐标表示为x,z坐标分别处以3200后的结果。如坐标为（6400,3200）的点用网格点表示即为（2,1）。
   网格：以网格点为中心，x,z±1600的正方形范围内的区域称为一个网格。如网格点（2,1）表示（4800,1600）至（8000,4800）之间的正方形区域。
   网格坐标：在一个网格内，以x,z最小的地方为原点，x增加的方向为x正方向，z增加的方向为z的正方向，构建新的坐标系。此时的坐标称为网格坐标。如网格点（2,1）中，网格坐标为（0,0）的点在游戏中的坐标为（4800,1600），游戏中坐标为（6400,3200）的点的网格坐标为（1600,1600）。
使用的计分板：
        journey_postx、journey_postz表示玩家的网格坐标
        journey_postcx、journey_postcz表示网格点
1、计算玩家所在网格点
      为确认玩家会触发哪个网格点的生成，以及考虑到网格点(0,0)不会生成驿站，故首先应计算玩家所在网格点。
      首先获取玩家的坐标，并保存至计分板上，后加上修正值1600并除以3200。这样即可得到玩家所在网格点。

journey:chunk/structures/post.mcfunction（部分）     用于生成驿站之前的部分计算
  1. execute store result score @s journey_postx run data get entity @s Pos[0]
  2. execute store result score @s journey_postz run data get entity @s Pos[2]
  3. scoreboard players add @s journey_postx 1600
  4. scoreboard players add @s journey_postz 1600
  5. scoreboard players operation @s journey_postx %= 3200 worlddata
  6. scoreboard players operation @s journey_postz %= 3200 worlddata
复制代码

2、计算玩家的网格坐标
      由于需要判断玩家是否进入驿站生成区域，并判断何时强加载区块，何时卸载强加载区块，故需要计算玩家的网格坐标。
      和网格点的计算一样，获取坐标后需要加上1600的修正值，之后模除3600即可。

journey:chunk/structures/post.mcfunction（部分）     用于生成驿站之前的部分计算
  1. execute store result score @s journey_postcx run data get entity @s Pos[0]
  2. execute store result score @s journey_postcz run data get entity @s Pos[2]
  3. scoreboard players add @s journey_postcx 1600
  4. scoreboard players add @s journey_postcz 1600
  5. scoreboard players operation @s journey_postcx /= 3200 worlddata
  6. scoreboard players operation @s journey_postcz /= 3200 worlddata
复制代码

3、判断强加载区块并检查标记
      当玩家到达网格点±160的范围内时，即玩家的x,z网格坐标均在1440~1760之间时，开始强加载网格点所在区块并检测标记。
      首先在玩家所在位置的y=-10处生成一个as(拥有journey_postdetector标签)，获取其x,z坐标并加上修正值1600，除以3200后再乘以3200，即可将其传送至网格点处。后强加载该区块，并检测是否有标记(另一个拥有journey_postmarker标签的as，并在计分板上储存自己的网格点)。如果没有标记，则在该位置生成标记并进行一次驿站的生成尝试

journey:chunk/structures/post/detect.mcfunction     用于检测标记
  1. summon armor_stand ~ -10 ~ {Tags:["journey_postdetecter"],NoGravity:1b}
  2. execute as @e[type=armor_stand,tag=journey_postdetecter] at @s run function journey:chunk/structures/post/tp
  3. execute at @e[type=armor_stand,tag=journey_postdetecter] unless entity @e[type=armor_stand,tag=journey_postmarker,distance=..10] at @s run function journey:chunk/structures/post/mark
  4. kill @e[tag=journey_postdetecter]
复制代码

journey:chunk/structures/post/tp     用于将检测as传送至网格点
  1. execute store result score Pos worlddata run data get entity @s Pos[0]
  2. scoreboard players add Pos worlddata 1600
  3. scoreboard players operation Pos worlddata /= 3200 worlddata
  4. scoreboard players operation Pos worlddata *= 3200 worlddata
  5. execute store result entity @s Pos[0] double 1 run scoreboard players get Pos worlddata
  6. execute store result score Pos worlddata run data get entity @s Pos[2]
  7. scoreboard players add Pos worlddata 1600
  8. scoreboard players operation Pos worlddata /= 3200 worlddata
  9. scoreboard players operation Pos worlddata *= 3200 worlddata
  10. execute store result entity @s Pos[2] double 1 run scoreboard players get Pos worlddata
  11. execute at @s run forceload add ~ ~
复制代码

journey:chunk/structures/post/mark.mcfunction（部分）     用于做标记，同时进行驿站生成尝试（未列出）
  1. summon armor_stand ~ -10 ~ {Tags:["journey_postmarker"],NoGravity:1b}
  2. execute as @e[tag=journey_postmarker,sort=nearest,limit=1] at @s run function journey:chunk/structures/post/tp
  3. scoreboard players operation @e[tag=journey_postmarker,sort=nearest,limit=1] journey_postcx = @p journey_postcx
  4. scoreboard players operation @e[tag=journey_postmarker,sort=nearest,limit=1] journey_postcz = @p journey_postcz
  5. #之后会尝试生成驿站
复制代码

4、强加载区块的卸载
      当地图充分探索时，强加载区块数量也会很大，可能影响性能。故我在优化时，增加了强加载区块卸载的判定。
      execute拥有journey_postmarker标签的盔甲架，判断是否有在该网格的玩家，以及这些玩家的网格坐标是否在指定范围内。当判定±196的范围内没有玩家时，即该网格没有玩家的网格坐标在1404~1796之间时，即可卸载该网格点所在区块。

journey:20ticks.mcfunction（部分）     游戏内每20ticks（1秒）执行的命令
  1. execute as @e[type=armor_stand,tag=journey_postmarker] at @s run function journey:chunk/structures/post/uninstall
复制代码

journey:chunk/structures/post/uninstall.mcfunction     用于判断网格点是否需要被卸载
  1. tag @s add journey_detecting

我有疑问
1、为什么计算网格点时需要加上1600的修正值？
      主要目的是为了让网格点成为网格的中心。
      如果不加上1600的修正值，网格点就不是网格的中心，而是网格的西北角。这会造成很大的不便，因为在判定一个网格点的生成时，需要在这个网格点相邻的4个网格点各自进行判断，非常复杂。而将网格点变成网格的中心，就只需要在一个网格点内检测即可，非常方便。
2、为什么强加载的卸载判定范围比加载判定范围大？
      主要是为了减少玩家频繁穿过加载、卸载判定的临界范围时，网格点所在区块被频繁加载、卸载的情况，以此来优化性能。
